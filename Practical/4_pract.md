# Описание архитектуры системы мониторинга IoT-телеметрии с устойчивым алертингом

## 1. Назначение системы

Система предназначена для приёма, обработки, хранения и визуализации телеметрии с IoT-датчиков в условиях **нестабильной сети**. Ключевые требования:

- Данные не теряются и не дублируются даже при обрывах связи.
- Показания восстанавливаются в правильном хронологическом порядке.
- Алертинг срабатывает не от единичного скачка, а при **удержании значения выше порога** в течение заданного времени.
- Сброс тревоги происходит **постепенно** (гистерезис), без «дребезга».
- Подписчики получают новые значения **мгновенно**.
- Вся история показаний сохраняется для аналитики.

Архитектура построена по событийно-ориентированному принципу и разделена на **5 логических слоёв**.

---

## 2. Слой приема (Ingestion Layer)

**Расположение на схеме:** левая голубая зона.

### Компоненты:

| Компонент | Назначение |
| :--- | :--- |
| **IoT Датчики** (актор) | Источник данных. Работают в условиях нестабильной связи. |
| **API Gateway / MQTT Broker** | Точка входа. Принимает HTTP/MQTT-запросы от устройств. |
| **Ingestion Service** | Сервис первичного приёма «сырых» данных. |

### Как это работает:

1. **IoT Датчик** собирает показания. Если связь с сервером пропадает, устройство **накапливает данные в локальном буфере** и запоминает их.
2. Когда связь восстанавливается, датчик отправляет **всю накопленную пачку** на **API Gateway / MQTT Broker**.
3. **API Gateway** принимает запрос и передаёт его в **Ingestion Service**.
4. **Ingestion Service** выполняет только первичную обработку — валидацию формата и немедленную публикацию в очередь. Тяжёлые вычисления здесь **не выполняются**, чтобы не задерживать приём.



---

## 3. Слой буферизации (Message Broker)

**Расположение на схеме:** жёлтая зона «Буферизация».

### Компонент:

| Компонент | Назначение |
| :--- | :--- |
| **Message Broker** (Kafka / RabbitMQ) | Очередь сообщений. Буфер между приёмом и обработкой. |

### Как это работает:

1. **Ingestion Service** публикует «сырые» данные в очередь (`Публикация` на схеме).
2. Очередь **сглаживает пиковые нагрузки**: если датчики одновременно прислали накопленные пачки, данные не потеряются, а будут обработаны по мере возможности.
3. Обеспечивает **асинхронность**: датчик отправил данные и «забыл» о них, а система обработает их тогда, когда сможет.

## 4. Слой обработки (Processing Layer)

**Расположение на схеме:** фиолетовая зона «Слой обработки».

### Компоненты (цепочка обработки):

| № | Компонент | Назначение |
| :--- | :--- | :--- |
| 1 | **Stream Processor** | Сортировка по времени |
| 2 | **Модуль дедупликации** | Проверка Sequence ID |
| 3 | **Rule Engine & State Manager** | Логика гистерезиса и алертинга |

### Как это работает:

**Шаг 1. Stream Processor (Сортировка по времени)**
- Вычитывает поток из **Message Broker** (`Чтение потока` на схеме).
- Поскольку данные приходят пачками и с задержкой, они могут быть перемешаны. Процессор **сортирует их по Timestamp генерации**, а не по времени прихода.
- Передаёт данные в модуль дедупликации.

**Шаг 2. Модуль дедупликации (Проверка Sequence ID)**
- Каждое сообщение имеет уникальный `Sequence ID`.
- Если пришёл ID меньше последнего обработанного — сообщение **устарело** и отбрасывается.
- Если пришёл ID, который уже обрабатывался — это **дубликат**, он игнорируется.
- Чистые данные передаются в Rule Engine.

**Шаг 3. Rule Engine & State Manager (Логика гистерезиса)**
- Это «мозг» системы. Применяет правила алертинга.
- **Не отправляет алерт от единичного скачка.** Вместо этого:
  - Записывает в **State Cache (Redis)** статус `WARNING` и время начала превышения порога.
  - Ждёт, пока значение продержится выше порога заданное время (например, 5 минут).
  - Только после этого генерирует событие `ALERT` и передаёт его в **Alert Manager** (`Триггер алерта` на схеме).
- Параллельно передаёт данные в слой хранения:
  - **Запись истории** → в Time-Series DB.
  - **Обновление состояния** → в Redis.

## 5. Слой хранения (Storage Layer)

**Расположение на схеме:** красная зона «Слой хранения».

### Компоненты:

| Компонент | Назначение |
| :--- | :--- |
| **Time-Series DB** (InfluxDB) | Хранение полной истории показаний |
| **State Cache** (Redis) | Хранение только текущего состояния |

### Как это работает:

**Time-Series DB (InfluxDB):**
- Сюда **Rule Engine** пишет **всю историю** показаний (`Запись истории` на схеме).
- Используется для построения графиков, отчётов, аудита.
- Отвечает за требование *«показания хранятся как история по времени»*.

**State Cache (Redis):**
- Сюда **Rule Engine** пишет **только текущее состояние** каждого датчика (`Обновление состояния` на схеме).
- Хранит: последнее значение, статус (`WARNING` / `OK`), время начала превышения порога.
- Работает в оперативной памяти, обеспечивая **мгновенный доступ**.
- Именно отсюда **Notification Service** берёт свежие значения для рассылки (`Мгновенная отправка новых значений` — пунктирная стрелка на схеме).

> **Решаемая проблема:** разделение «тяжёлой» истории и «быстрого» текущего состояния для обеспечения и аналитики, и real-time.

## 6. Слой оповещения (Alerting Layer)

**Расположение на схеме:** зелёная зона «Слой оповещения».

### Компоненты:

| Компонент | Назначение |
| :--- | :--- |
| **Alert Manager** | Таймеры и пороги |
| **Notification Service** | WebSockets / Push |
| **Подписчики** (актор) | Клиенты |

### Как это работает:

**Alert Manager (Таймеры и пороги):**
- Получает от **Rule Engine** сигнал `Триггер алерта (Порог + Время)`.
- Проверяет, что значение держится выше порога **дольше заданного времени**.
- Если условие выполнено — генерирует событие `ALERT` и передаёт его в Notification Service.

**Notification Service (WebSockets / Push):**
- Получает события от **Alert Manager** (тревоги).
- Получает свежие значения от **State Cache (Redis)** по пунктирной стрелке `Мгновенная отправка новых значений`.
- Рассылает данные подписчикам через **WebSockets** (для real-time) или **Webhooks** (`Push / Webhook` на схеме).

**Подписчики (Клиенты):**
- Дашборды, мобильные приложения, внешние системы.
- Получают как мгновенные обновления значений, так и тревожные уведомления.

> **Решаемая проблема:** мгновенная доставка данных и своевременное оповещение без «дребезга».

## 7. Логика гистерезиса (пример работы)

Рассмотрим пример: **порог = 100°C, удержание = 5 минут, сброс при 95°C.**

| Шаг | Событие | Действие системы |
| :--- | :--- | :--- |
| 1 | Датчик: **105°C** | Rule Engine видит `> 100`. Записывает в Redis: `status = WARNING`, `start_time = 12:00`. Алерт **не отправлен**. |
| 2 | Датчик: **102°C** | Статус уже `WARNING`. Таймер продолжает идти. Алерт **не отправлен**. |
| 3 | Датчик: **98°C** | Упало ниже 100, но выше 95. Алерт **не снимается** (защита от дребезга). |
| 4 | Прошло 5 минут, значение всё ещё `> 100` | **Alert Manager** генерирует `ALERT` → уходит подписчикам. |
| 5 | Датчик: **94°C** | Упало ниже 95 → алерт постепенно снимается, статус меняется на `OK`. |

> Такая логика полностью соответствует требованию: *«срабатывает не от единичного скачка, а если значение держится выше порога всё время, и успокаивается постепенно»*.

## 8. Соответствие требований и решений

| Требование из ТЗ | Решение в архитектуре |
| :--- | :--- |
| Нестабильная связь | Локальный буфер на датчике + Message Broker |
| Без потерь | Очередь (Kafka / RabbitMQ) + подтверждения доставки |
| Без дублей | Модуль дедупликации по `Sequence ID` |
| Правильный порядок | Stream Processor — сортировка по `Timestamp` |
| Алерт не от скачка | State Manager в Redis хранит `start_time` |
| Постепенное успокоение | Rule Engine — гистерезис (сброс при 95°C, а не при 100°C) |
| История по времени | Time-Series DB (InfluxDB) |
| Мгновенные значения | State Cache (Redis) + Notification Service (WebSockets) |

## 9. Технологический стек (рекомендуемый)

- **Брокер сообщений:** Apache Kafka или RabbitMQ
- **База данных временных рядов:** InfluxDB
- **Кэш / State Store:** Redis
- **Протоколы:** MQTT (для датчиков), WebSockets (для клиентов)
- **Язык разработки:** Python (FastAPI) или Go
